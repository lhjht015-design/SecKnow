## EXP-0024 — 变换单元全走批量 Y

**背景**：EXP-0023 只把批量 Y 接进检测与前缀分数；变换单元的探测仍逐个走 E/R。

**改动**：`call_many` 全部走 Y（8 路并发、保序）；`verify_plain` 同步；建表单元
增加“表复用 + 常量差分”（5 个采样值判断是否等于已有表 ^ 常量）。

**靶场**：新增 `chal_sbox_elf` / `chal_perm_elf` / `chal_gf2_elf`，
加上已有的仿射程序，四条路径各有载体。

| 题 | 路径 | 探测数 | 耗时 |
| --- | --- | --- | --- |
| V1 S 盒建表 | `invert_bytewise_table` | 1465（原 5331） | 约 11 s（原 39 s） |
| V2 逐字节仿射 | `invert_bytewise_affine` | 206 | 约 1 s |
| V3 位置置换 | `invert_permutation` | 145 | 约 1 s |
| V4 GF(2) 线性 | `invert_gf2` | 272 | 约 2 s |

正样本 4/4，连续 3 次一致，平均约 3.7 s/题。

**四个关键点**（`laws/LAW-0030.md`）：
1. 批量 Y 对结果型探测安全。
2. 256n 不是必须的：5 点差分把建表降到约 n×5 + 4×256。
3. 复用可证伪：5 点只是候选，最终由重新加密兜底。
4. 四条路径由依赖矩阵各自选中。

## EXP-0023 — 并行探测优化

**背景**：EXP-0022 的爬坡是串行的。改造 worker 支持批量并发，验证哪些探测能并发。

**改动**：worker 新增 `Q`（批量耗时）与 `Y`（批量结果），8 路线程池、保序回传；
时序爬坡按轮执行；阈值封顶 5ms + 逐步 gap 中位数 + 最多 3 次重试。

| 题 | v024 串行 | v025 并行 |
| --- | --- | --- |
| T2 Python 时序 | 约 3.2 s | 约 1.3 s |
| R1 ELF 数字前缀 | 约 3.5 s | 约 2.0 s |
| T1 ELF 时序 | 约 11–16 s，偶发失败 | 约 11 s，稳定 |
| E4 ELF 变换 | — | 约 1.5 s |

正样本 4/4，负样本 2/2，连续 3 次一致，平均约 3.2 s/题。

**关键负结果**：ELF 时序并行批测把噪声从 ±2ms 抬到 ±10ms（16 路），
6ms 的信号被淹没；4 路仍有 ±4ms。所以 ELF 时序保持串行，只有 Python 并行。

**四条结论**（`laws/LAW-0029.md`）：
1. 并发只对结果型探测安全，时序型并发会污染要测的量。
2. 进程启动是 ELF 的噪声地板。
3. 阈值封顶 + 逐步 gap 中位数 + 重试是鲁棒性的关键。
4. 批量协议保序但每任务独立计时。

## EXP-0022 — 时序侧信道前缀爬坡

**背景**：有些校验器 stdout、退出码都恒定，只有"每匹配一个字节多花一点时间"。

**靶场**：`chal_timing`（ELF 6ms/byte）、`p7_timing.src`（Python 2ms/byte）、
`chal_timing_const`（恒定 5ms）、`chal_timing_faint`（0.2ms/byte）。

**检测**：100 个探测测耗时，峰值 − 中位数 > 阈值（ELF 4ms / Python 2ms），
再对峰值输入复测 3 次确认。

**爬坡**：每个位置先用 `0x01` 测基线；按 `flag{}_` + 字母频率序扫描，
命中即确认并早停；每步要求"确认 − 基线" > 0.5×延迟；结束时用
"完整候选 vs 首字节打错"验证整串长度。

| 题 | 接口 | 结果 | 探测数 |
| --- | --- | --- | --- |
| T1 ELF 6ms/byte | `timing` | ✓ 约 11 s | 387 |
| T2 Python 2ms/byte | `timing` | ✓ 约 3 s | 377 |
| R1 数字前缀（回归） | `check_num` | ✓ | 419 |
| N1 恒定 5ms | `none` | ✓ 拒绝 | 0 |
| N2 0.2ms/byte | `none` | ✓ 拒绝 | 0 |

正样本 3/3，负样本 2/2，平均约 4.1 s/题，连续 3 次一致。

**五个关键点**（`laws/LAW-0028.md`）：
1. 时序成本是平方级（每次探测重放已知前缀）；第一版全字符集扫描跑了 447 s。
2. 基线 + 频率序早停把 T2 从 447 s 压到 2.8 s。
3. 检测必须复测峰值：0.2ms 的弱信号曾被噪声尖峰误判成 timing。
4. 位置级 margin 是时序版的执行验证。
5. 结束验证检查整串长度，而不是只看最后一个字节。

**边界**：要求逐字节早退比较；常数时间/先哈希的校验器无法利用；
ELF 需要 ≥6ms/字节压过进程启动噪声。

## EXP-0021 — ELF 校验器的前缀接口

**背景**：EXP-0020 的 ELF 后端只能处理 stdin→stdout 变换，校验器只能拒绝。
真实逆向题里校验器常泄露"正确前缀长度"。

**接口检测**：探测集 = 空串 + 95 个可打印单字符 + 长度 1–4 的串 + 重复项。

| 判据 | 接口 |
| --- | --- |
| 输出长度 == 输入长度 | `enc` |
| stdout 归一成 0..len 且随输入变化 | `check_num` |
| 退出码在 0..len 且随输入变化 | `check_exit` |
| 其它 | `none` |

归一化支持纯数字、`prefix=N`、`correct=N`；退出码直接使用。
三种信道统一成 `oracle.call(x) -> int`，复用 `solve_prefix_checker`。

| 题 | 接口 | 结果 | 探测数 |
| --- | --- | --- | --- |
| E1 stdout 纯数字 | `check_num` | ✓ | 322 |
| E2 `prefix=N` | `check_num` | ✓ | 318 |
| E3 退出码 | `check_exit` | ✓ | 337 |
| E4 ELF 变换（回归） | `enc` | ✓ | 123 |
| N5 只回 wrong | `none` | ✓ 拒绝 | 0 |
| N6 恒输出 0 | `none` | ✓ 拒绝 | 0 |

正样本 4/4，负样本 2/2，平均约 2.3 s/题，连续 3 次一致。

**四个关键点**（`laws/LAW-0027.md`）：
1. 接口的本质是有序信号，不是输出格式。
2. 检测必须要求分数随输入变化（N6 恒定数字是陷阱）。
3. 退出码是第二信道，上限 0..255。
4. 探测集要遍历可打印首字符，才能看到 score 分岔。

**边界**：只支持泄露前缀长度的校验器；ELF 每题约 300 次进程启动。

## EXP-0020 — 按附件自动建立 oracle 入口

**背景**：EXP-0019 的黑盒入口依赖题面出现技术词。真实比赛常常只给附件。

**识别规则**：`PK..` → zip（递归成员）；`\x7fELF` → ELF（WSL 逐次执行）；
后缀 `.py/.src` 或内容含 `def enc/check` → Python（AutoOracle 握手 enc/check/none）；
可打印文本 → 数据（按形态加提示）；其它 → `attachment_unknown`。

入口建立后所有策略单元可用，选择交给结构分类与 guard。

| 题 | 识别 | 结果 | 路径 / 原因 | 探测数 |
| --- | --- | --- | --- | --- |
| A1 `.src` | python | ✓ | `probe_facts → classify → invert_bytewise_affine → verify` | 153 |
| A2 改名 `.dat` | python | ✓ | 按内容识别，同上 | 178 |
| A3 zip 内脚本 | python | ✓ | `… → invert_bytewise_table → verify` | 4450 |
| A4 ELF 变换 | elf | ✓ | `… → invert_bytewise_affine → verify` | 117 |
| A5 文本 hex | text | ✓ | `xor_single_byte` | 0 |
| A6 文本 base64 | text | ✓ | `base64_chain` | 0 |
| N1 随机二进制 | unknown | ✓ 拒绝 | `attachment_unknown` | 0 |
| N2 无入口脚本 | python | ✓ 拒绝 | `no_enc_or_check` | 0 |
| N3 zip 无可用成员 | unknown | ✓ 拒绝 | `zip_no_usable_member` | 0 |

正样本 6/6，负样本 4/4，平均 270 ms/题，连续 3 次一致。

**四个关键点**（`laws/LAW-0026.md`）：
1. 后缀可伪造，内容与魔数不会（A2）。
2. zip 是容器不是类型，要递归成员。
3. ELF 后端让编译程序与脚本同权；每次探测一个进程。
4. 文本附件按形态路由，不需要题面技术词。

**边界**：ELF 仅支持 stdin→stdout 无状态变换；无 ELF check 模式；
zip 深度 ≤2；误判只会导致拒绝，不会伪造答案。

## EXP-0019 — 8 个黑盒单元并入文本召回库

**背景**：v007 靠关键词从题面召回数据单元，v020 靠状态类型规划黑盒单元。

**统一库（14 个）**：4 个常驻基础设施 + 5 个黑盒策略 + 5 个文本数据单元。

**新增 P6**：主办方脚本 = 先 Base64 再逐字节 S 盒。规划路径跨家族：

```
probe_facts → classify → invert_bytewise_table → verify_plain
            → bytes_to_text → base64_chain
```

没有任何专用胶水代码，靠状态类型（verified → text）接上。

| 组 | 结果 |
| --- | --- |
| T1–T5 文本题 | 5/5 |
| P1–P6 黑盒题（含组合） | 6/6 |

4. 同一份 DFS/Refuse/验证闸门处理两种输入。

**诚实限制**：文本召回仍是关键词匹配，LAW-0011 的改名塌陷未解决；

## EXP-0018 — 黑盒反解策略接入契约单元库

接进与 v007/v009 相同的类型化规划器。

| --- | --- | --- |

| P2 | `… → invert_bytewise_affine → verify` | 124 |
| P3 | `… → invert_gf2 → verify` | 220 |

## EXP-0017 — 黑盒刻画：不读逻辑也能反解

**背景**：LAW-0017 显示 61.7% 的真实步骤是题目特有逻辑，检索变不出来。
本实验验证另一条不用 LLM 的路：不读源码，把出题人的脚本当 oracle，用探测刻画结构。

**挑战**（`experiments/EXP-0017/chal/*.src`，故意写得没有语义）：

| 题 | 结构 |
| --- | --- |
| P1 | 四张自定义 S 盒按位置轮换 + 位置常量 |
| P2 | `out[i] = 0x9D*x[i] + B[i] (mod 256)` |
| P3 | 整块 GF(2) 随机可逆矩阵（L·U 构造） |
| P4 | 三轮 Feistel，轮函数 = 循环移位 + 常量 |
| P5 | 只返回"正确前缀长度"的校验器 |
| N1 | sha256（单向、长度不保持） |
| N2 | 32 位非线性混合（乘法 + 移位异或） |
| N3 | 每次调用换随机掩码 |

**判定顺序**：确定性 → 长度保持 → 依赖矩阵 → 逐字节（先仿射、后建表）/
置换 / GF(2) 线性 → 前缀爬坡；每一步都不成立就拒绝。

| 题 | 结果 | 策略 / 原因 | 探测数 |
| --- | --- | --- | --- |
| P1 | ✓ | `bytewise_table` | 6278 |
| P2 | ✓ | `bytewise_affine` | 124 |
| P3 | ✓ | `gf2_linear` | 220 |
| P4 | ✓ | `gf2_linear` | 239 |
| P5 | ✓ | `prefix_oracle` | 375 |
| N1 | ✓ 拒绝 | `not_length_preserving` | 13 |
| N2 | ✓ 拒绝 | `structure_unknown` | 232 |
| N3 | ✓ 拒绝 | `nondeterministic` | 3 |

正样本 5/5，负样本 3/3，总计 7484 次探测、平均 22.9 ms/题。

**最重要的三条**（`laws/LAW-0023.md`）：
1. "读懂逻辑"可以换成"刻画行为"；依赖矩阵 n 次探测就能分开逐字节/置换/全混合。
2. GF(2) 线性检测拆穿了"看起来非线性"的 Feistel——轮函数线性，整体仍是仿射。
3. 校验器只要泄露前缀进度，逐字节爬坡就能拿到 flag；只回 "wrong" 则不在覆盖内。

**边界**：必须能执行 oracle；只覆盖确定、长度保持、逐字节双射/置换/GF(2) 仿射；
真正的非线性构造仍需符号执行或人工阅读。

## EXP-0016 — canary + PIE + ret2libc 三保护组合

**背景**：v015 只会绕保护，v016 只会 ret2libc；真实题通常三者同时成立。
三样信息必须在同一进程里按依赖顺序拿。

**靶场**（`experiments/EXP-0016/lab/`）：

| 文件 | 说明 |
| --- | --- |
| `vuln4` | `while(1){ puts("input:"); vuln(); }`，`buf[128]` + `read(0x200)` + `printf(buf)`；`-fstack-protector-all -pie -fPIE` |
| `vuln4_noleak` | 同样保护，但 printf 用常量格式串，没有可控泄漏 |
| `libc.so.6` | 题目附带 libc |

**三段式**

| 轮次 | 载荷 | 得到 |
| --- | --- | --- |
| 1 | `AAAAAAAA + "%p,"×N + NUL` | idx0 → canary + saved rip → PIE 基址 |
| 2 | `%<idx0+2>$s` + 指针槽 | puts 运行时地址 → libc 基址 |
| 3 | canary + saved rbp + ret + pop_rdi + binsh + system | shell → flag |

| 题 | 结果 | 原因 |
| --- | --- | --- |
| T1 | ✓ 约 1.18 s | 真实执行拿到 flag |
| N1 错 libc 偏移 | ✓ 如实拒绝 | `libc_mismatch` |
| N2 无可控泄漏 | ✓ 如实拒绝 | `leak_failed` |

连续 3 次稳定，平均约 490 ms/题。

**六个关键点**（`laws/LAW-0022.md`）：
1. 三样信息必须同进程、按依赖顺序拿；
2. `"%p,"` 是 3 字节，泄漏串必须严格小于 canary_offset——按 2 字节估算会写坏 canary，
   现象是 `*** stack smashing detected ***`；
3. read 不补 NUL，泄漏串末尾必须加 `\x00`；
4. idx0 用 `0x4141414141414141` 标记现场标定；
5. `%s` 的指针放在格式说明之后（GOT 地址含 `00`）；
6. 栈对齐仍需额外 `ret`。

## EXP-0013 — canary / PIE 绕过

| 题 | 保护 | 结果 |
| --- | --- | --- |

| P1 | PIE | ✓ |
| B1 | canary + PIE | ✓ |
| N1 | 无泄漏原语 | ✓ 如实失败（`leak_stage_not_found`） |

**五个关键点**（`laws/LAW-0019.md`）：
1. 泄漏与利用必须同进程；

**结果**

| --- | --- | --- | --- |

**首轮出现过一个假通过**：`read_text` 当时接受所有文件类型，把二进制按 latin-1 解码，
flag 是明文就被"蒙对"了——F5/F6 一步完成，**等于没验证 pcap/elf 路由**。
把 `read_text` 收紧到只接受 `file:bin` 后重跑，路径才变成
`pcap_strings` / `elf_strings`，通过率不变但验证才成立。
→ 结论：**看路径，不只看结果。**（`laws/LAW-0015.md`）

## EXP-0008 — 混合场景：先解码再走 RSA

**要回答的问题**：真实题是异构的——"先 Base64 解码，解出来是 RSA 的 n/e/c"。
规划器的状态如果只会是字符串，就走不到结构化单元。

**改动**：状态值扩展为 `str | dict[str, int]`；新增类型 `int_fields`；
新增 `parse_int_fields`（text → int_fields）与 `rsa_small_e`（int_fields → flag）。

**结果**

| 题 | 实际路径 | 结果 |
| --- | --- | --- |
| M1 `base64("n/e/c")` | `b64_decode → parse_int_fields → rsa_small_e` | ✓ |
| M2 `hex("n/e/c")` | `hex_decode → parse_int_fields → rsa_small_e` | ✓ |
| M3 三层编码 | `b64 → hex → b64 → parse_int_fields → rsa_small_e` | ✓ |
| M4 中文标签 + 十六进制数值 | `parse_int_fields → rsa_small_e` | ✓ |
| N1 `e=65537`（负样本） | 解析成功，但 RSA 单元判断不适用并拒绝 | ✓ 正确失败 |
| N2 4 字节 XOR（负样本） | 无对应单元 | ✓ 正确失败 |

正样本 **8/8**（4 题 × 2 种题面），负样本 **4/4 正确失败**。
加 9 个诱饵单元后：beam 8/8（224 节点），BFS 6/8（329 节点）——与 EXP-0007 结论一致。

**最有价值的一条**：N1 说明"解析成功 ≠ 能解"。`parse_int_fields` 正确抽出了 n/e/c，
但 `rsa_small_e` 检测到 `e=65537` 不满足小公钥指数条件，**主动拒绝**，
而不是硬算出一个错误结果。单元必须对自己不适用的情况显式报错。

## EXP-0007 — 多步组合验证

**要回答的问题**：真实赛题大多是多步的，能不能**自动规划**出正确的单元序列并跑通？

**做法**：类型化搜索。单元声明 `accepts` / `produces`，规划器每步选一个能接受当前类型的
单元，**真实执行**，重新识别形态后继续；执行异常 / 状态重复即剪枝。

| 搜索 | 5 单元 | 8 单元 | 12 单元 | 20 单元 |
| --- | --- | --- | --- | --- |
| BFS | 8/8 | 8/8 | **6/8** | **6/8** |
| beam | 8/8 | 8/8 | **8/8** | **8/8** |

- 覆盖深度 1–4，包括 `b64 → hex → b64 → XOR` 四层嵌套；
- 两种题面（明说技术名 / 只描述行为）结果一致；
- **负样本（多字节 XOR，库里没有对应单元）在两种搜索下都正确失败**（2/2）。

**两条结论**
1. **组合机制成立**：类型 + 真实执行 + 剪枝，可以把多个契约单元串成一条可验证的流水线。
2. **必须做搜索控制**：朴素 BFS 的分支数 ≈ 单元数，深度 4 时是 |U|⁴ 量级；
   加上"解码/编码方向先验 + beam 预算"后，20 个单元仍能保持 8/8。

**诚实限定**：单元库只有 5–20 个，题目是合成链。这验证的是**机制**，不是真实赛题能力。
另外我在调试中修了一个测试自身的 bug（加密层顺序写反），修前 S3 全挂。

## EXP-0006 — 分布漂移测试（对"真实赛题"的第一次压力测试）

**背景**：用户指出 v007 的 5/5 是自己出题、自己写单元，正对应他踩过的坑——
"在我们题库里表现很好，遇到主办方真实题目就不行，因为变量名会换、函数名会换、
实现逻辑很抽象"。

**设计**：同一批 5 个技术，每题做三档陌生度。

| 档位 | 改动 |
| --- | --- |
| L1 | 技术名明确、参数名标准（v007 基线） |
| L2 | 参数名改中文别名、数值改十六进制、数据放进 JSON |
| L3 | **完全不提技术名**，只描述行为（"每个字节与同一个常数做同一种运算"） |

**结果**

| 召回策略 | L1 | L2 | L3 | 合计 |
| --- | --- | --- | --- | --- |
| keyword-only | 5/5 | **1/5** | **0/5** | 6/15 |
| shape-only | 5/5 | 5/5 | 5/5 | 15/15 |
| hybrid | 5/5 | 5/5 | 5/5 | 15/15 |

**结论**
1. **改名会让关键词召回几乎归零**——这解释了"题库里好、真题上不行"的现象。
2. **数据形态路由免疫改名**：变量名可以改，但"2048 位整数""长 hex""8 位 CRC + 字母范围"
   这些形状改不掉。所以召回应当基于结构，而不是技法词。
3. **但边界必须说清楚**：这套方法只能消除"命名差异"，不能消除"逻辑新颖性"。
   主办方自己发明的变换，题库里没有对应单元，检索再准也找不到。

**诚实限定**：L2/L3 仍是我写的；且调试过程中我修了 3 个自己抽取器的 bug
（小整数 e 被跳过、形态识别与抽取口径不一致、只给 2 个大整数时判定失败），
所以 15/15 部分来自"看着失败样例调规则"。**这不是泛化证明。**

## EXP-0005 — 代码单元召回与拼装

**要回答的问题**：能不能把代码拆成结构化单元，按题目召回，再拼成**真正能运行**的脚本？

| 路线 | 文件 | 做法 | 结果 |
| --- | --- | --- | --- |
| A 抓取式 | `v006_code_units.src` | 抽 1165 个单元 → FTS 召回 → 按"变量名像不像 n/e/c"猜槽位 | **0/5** |
| B 契约式 | `v007_solver_kit.src` | 单元显式声明 params/returns/technique → 按契约绑定 → 执行校验 | **5/5** |
| B 端到端 | `v007_solver_kit.src --demo-text` | 只给题目文本，参数由每个单元的正则抽取器取出 | **5/5**（约 1 秒，零模型） |

**A 的失败诊断（最有价值的部分）**：正确的单元**其实都召回到了**——
RSA 命中 `rsa1.py`、CRC32 命中 `crack_crc()`、凯撒命中 `variant_caesar()`。
失败全在适配：无关常量被当成必填槽位、函数无 driver、变量名不在别名表就判定无槽位、
把加密函数当解密函数调用。

→ **"拆分"本身不产生可拼装性，可拼装性来自显式契约。**（`laws/LAW-0010.md`）

**对照**：qwen3:8b 单次生成在 9 道可执行题上是 **1/9**，67% 给出错误 flag；
契约化拼装 5/5，且每次产出都经过真实执行验证。

**局限**：5 个单元是手工最小验证集，不是泛化证明；真实成本在把知识库约 250 个
可复用脚本改造成带契约的单元。参数抽取器按单元手写，真实赛题会更脏，
但失败是显式的（`param_extract_failed`），不会静默给出错误脚本。

## EXP-0004 — SAG2 式离线多跳检索（关键实验）

**文件**：`versions/v005_sag2_multihop.src`

**要回答的问题**：SAG2（embedding-free 多跳）能不能离线用？比原来的单跳 + 向量强多少？

**重要前提**：SAG2 论文里的 **JEV 是在线判官 API**（`api.typesafe.ai`）。
我们把它换成本地判官，并做了两档：

| 配置 | 判官 | 是否用模型 |
| --- | --- | --- |
| A | `bge-reranker-v2-m3`（cross-encoder，判别式，不生成文本） | 用模型，但**不是生成式 LLM** |
| B | 无，直接按 BM25 分数排序 | **完全不用任何模型** |

**结果（120 题、同种子、同真值口径）**

| 指标 | 单跳 + reranker | 多跳 + reranker | 多跳、无模型 |
| --- | --- | --- | --- |
| `tag_recall@8`（原始，含自身文件） | 0.5925 | 0.994 | 0.994 |
| **`tag_recall_excl_self`（排除自身，真实能力）** | **0.160** | **0.175** | **0.109** |
| `similar_wp_rate_conditional` | 0.20 | **0.30** | 0.225 |
| `vuln_type_hit_rate` | 0.133 | **0.183** | 0.125 |
| 单题耗时 | 3.5 s | 5.5 s | **0.57 s** |
| Top-K 中 meta WP 占比 | 0.83 | 0.96 | 0.974 |

**三个必须一起看的结论**

1. **原始的 0.994 是假的**：`self_leak_rate = 1.0`，每题都检索到了自己的 meta 文件，
   而该文件含全部真值标签。排除自身后只有 **0.175**（见 `laws/LAW-0009`）。
2. **多跳确实有效，但增益中等**：在 reranker 判官下，
   `tag_recall_excl_self` 0.160→0.175（+9%），`similar_wp_conditional` 0.20→0.30（+50%），
   `vuln_type_hit` 0.133→0.183（+37%）。后者才是比赛现场"找相似题"真正用的指标。
3. **完全不用模型的版本可用，但质量下降**：0.109 vs 0.160，换来 **约 9 倍加速**（0.57 s/题）。
   如果赛事连神经模型都不允许，这是可交付的底线方案。

**为什么这对本项目重要**：它证明"离线、不用生成式 LLM"的推理路线是**可以做出效果**的——
词法多跳 + 判别式判官，全程不生成任何文本。

### EXP-0003 的作用

AI 在比赛现场不能用，所以平台的核心指标不是「AI 能不能解题」，而是
**「拿到一道题，能不能快速准确地找到该看的 WP / 知识章节 / payload」**。
这件事有真值：meta WP 的 `tags` 就是标准答案，1156 篇可以大规模自动评分。

查询只用 `title + contest + difficulty + vuln_type` 拼成，**刻意排除**
`tags` / `one_liner` / `attack_chain` / `key_payload`——那些是答案本身。

**最终数据（完整语料 16361 块）**

| 指标 | 值 |
| --- | --- |
| `tag_recall@8` | 0.593 |
| `self_leak_rate` | 0.825 |
| `similar_wp_rate` | 0.067 |
| `similar_wp_rate_conditional`（仅在有近似题的子集上） | 0.20 |
| `top_k_composition` | meta WP 83% / 大部头 PDF 8.6% / 其它 8.4% |
| `mean_meta_wp_per_query` | 5.0 / 8，且 0 题命中 0 篇 WP |
| 单次检索耗时 | 约 3.8 秒（GPU） |

**必须和原始指标一起看的两个前提**（否则会得出错误的优化方向，见 `laws/LAW-0007`）：

1. `similar_wp_rate` 的上界不是 1.0：整库只有 **318/1156（28%）** 的题存在共享 ≥2 标签的近似题。
2. 把 OCR 出的 3 本书加入语料后指标**下降**了（tag_recall 0.638→0.593），
   因为书籍块挤占了固定的 Top-K 名额。这是**多样性权衡**，不是回归。

**漏检标签**几乎全是只出现一次的专有词（`PTRACE_POKETEXT`、`XXTEA`、`RSA-public-key-PEM`），
说明瓶颈在**语料覆盖**，不在排序算法，也不在模型。

## EXP-0001 — 离线推理解题可行性判决性实验

**文件**：`versions/v001_feasibility_probe.src`

**要回答的问题**：离线（纯本地）推理能不能产出「真的能解」的 CTF 解题路径？

**为什么不采用 LLM 自评**：浙密杯的教训是「AI 每次都说能解，现场解不了」。
让 LLM 评价自己等于重新引入同一个失效模式。所以判据全部客观。

| 区 | 内容 | 判据 |
| --- | --- | --- |
| A | 7 道自带已知 flag 的可执行题（Base64 链 / 单字节 XOR / 凯撒 / RSA 小明文 / 二进制转换 / 逆向逻辑 / CRC32 爆破） | 模型写的代码被**真实执行**，stdout 出现正确 flag 才算解出 |
| B | 4 道知识接地问答 | 引用有效性、关键词覆盖率、幻觉引用率 |
| C | 3 道硬负样本（库里根本没有答案） | 是否明确弃答；未弃答即记为 FALSE_CONFIDENCE |

**关键指标**
- `A_solve_rate`：真的被解出的比例
- `A_false_positive_rate`：给出了 flag 但是错的 —— **「假能解」的直接量化**
- `B_ungrounded_citation_rate`：引用了不存在的证据编号的比例
- `C_false_confidence_rate`：对无答案的问题仍然自信作答的比例

**自检（--oracle）**：用参考解验证 7 道题都可解且 flag 一致。
首次运行即抓到 A3 的正则 bug（`[a-z]{5}` 应为 `{4}`）。**oracle 不过，模型失败就不可信。**

**预实验数据**（qwen2.5:3b-instruct-q4，`A` 区 7 题）
```
A_solve_rate                0.0
A_solved_by_exec            0
A_false_positive_rate       0.714     ← 7 题里 5 题给出了一个错误的 flag
A_mean_latency_s            6.7
```
其中最典型的一题：模型直接把答案硬编码成 `print("flag{HELLO_WORLD}")`——
既没解码，也不是正确答案，而题目明确要求"不要写死答案"。

## EXP-0002 — 带确定性验证的离线回答

**文件**：`versions/v003_verified_answer.src`

**要验证的假设**：在生成之后插入一道**确定性**验证闸门，能否拦住「结构完整但解不了」的方案？

**做法**：模型按固定格式产出分步方案，每步带证据编号与关键载荷；然后纯字符串/集合运算检查
（a）引用的编号是否存在、（b）关键载荷是否出现在**它自己引用的**证据里、（c）是否整步无引用。

**逻辑自测**（合成答案，无模型参与）

| 输入 | 期望 | 实际 |
| --- | --- | --- |
| 全部有据 | SUPPORTED | SUPPORTED ✓ |
| 含假引用 `[E7]` + 编造载荷 `LD_PRELOAD=/tmp/evil.so` | UNSUPPORTED | UNSUPPORTED ✓，且精确列出无据载荷 |
| 整步无引用 | UNSUPPORTED | UNSUPPORTED ✓ |

**真实模型试跑**（qwen2.5:3b，问题「PHP 命令执行漏洞怎么利用？给出具体 payload」）
```
判定                     UNSUPPORTED
步骤                     7
假引用                   0/7
无据载荷                 7/15 (46.7%)
```
模型把 PHP 命令执行问题答成了 SSRF payload（`expect://`、`?url=`），
闸门识别出这些载荷在它自己引用的证据里根本不存在，**拒绝输出完整方案**，
改为输出「证据不足」并逐条列出被拒绝的步骤。
