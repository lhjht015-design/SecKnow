date: 2026-11-11
source: 实验
topic: 并行探测不是万能的——结果型探测可以并发，时序型探测并发反而抬高噪声
hypothesis: 把 oracle 探测改成 worker 内 8 路并发后，时序爬坡与前缀爬坡的
            墙钟时间都会下降，且结果不变。
experiment:
  - worker 新增批量协议：
      Q <n> 后跟 n 行 hex → n 行耗时（微秒）
      Y <n> 后跟 n 行 hex → n 行结果（stdout|rc 或整数）
    父进程一次投递、顺序接收；worker 内 ThreadPoolExecutor(8) 并发执行。
  - 爬坡按"轮"执行：基线 3 次、候选按 16 个一批、确认 3 次串行。
  - 对照（同机、同靶场，EXP-0022 vs EXP-0023）：
      T2 Python 时序（2ms/字节）      3.2 s → 1.3 s
      R1 ELF 数字前缀                3.5 s → 2.0 s
      T1 ELF 时序（6ms/字节）        并行失败；改回串行后约 11 s 稳定
      E4 ELF 变换（新增）            —      → 约 1.5 s
    正样本 4/4，负样本 2/2，连续 3 次一致。
  - 关键负结果：ELF 时序的并行批测把噪声从 ±2ms 抬到 ±10ms（16 路），
    6ms 的睡眠信号被淹没。4 路并发仍有 ±4ms，只能勉强区分。
result:
  - **四个关键点**：
    1. **并发只对"结果型"探测安全。** 变换/前缀分数只需要结果，
       并发不会改变正确性；时序探测需要"耗时"本身，并发会引入
       调度与进程启动的竞争噪声，正好污染要测量的量。
    2. **进程启动是 ELF 的噪声地板。** WSL 每次起进程约 4–30ms（随负载波动），
       并发时相互争抢；6ms 的信号在 16 路并发下不可靠。
       因此 ELF 时序保持串行，只有 Python（进程内 sleep 释放 GIL）并行。
    3. **阈值不能只由首步估计决定。** v024 用 `0.5×首步估计` 当阈值；
       首步被噪声抬高后阈值跟着抬高，后续位置把正确字符判成"不够快"。
       v025 把阈值封顶在 5ms，并用各步 gap 的中位数做结束验证，
       再加上最多 3 次重试，T1 从偶发失败变成稳定通过。
    4. **批量协议要保序但不必保时序。** worker 用 `map` 保序回传；
       每个任务在自己的线程里计时，排队时间不计入单次耗时。
       这一点保证了 Q 批量的单个测量仍然有效。
  - **收益的边界**：结果型探测的收益取决于"探测数 / 并发度"；
    R1 的 594 次探测在 8 路下仍要约 2 s，因为每次都是一个进程。
    Python 时序的收益最大（2.4×），因为调用在进程内且 sleep 释放 GIL。
conclusion:
  - 优化的正确姿势是"先分类，再并行"：
    结果型 → 并发；时序型 → 串行（进程外）或并发（进程内 sleep）。
    盲目并发会在最需要精度的地方引入噪声。
  - 阈值与重试是鲁棒性的一部分：时序攻击的失败模式是"某一步判错"，
    阈值封顶 + 逐步 gap 中位数 + 重试，把偶发噪声挡在结果之外。
next: 对 ELF 探测做"预热 + 固定 CPU 亲和"以降低启动抖动；
      把批量 Y 接入变换单元的全部探测路径；对超长表构建做分片并发。
