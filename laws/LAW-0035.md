```yaml
id: LAW-0035
prev: LAW-0034
date: 2026-11-12
source: 实验
topic: PDF 代码缩进要按字体分段 + 花括号重建；文本层本身常常没有编码逐行缩进
hypothesis: PDF 代码缩进是 normalize_text 压平的，换成 normalize_code_text 即可。
experiment:
  - 现象：PDF 页面此前整页作为一个 paragraph 元素，搜索出的 C/C++ 代码全部顶格。
  - 探查：
      - `page.get_text("text")` 里每行有统一的 4 空格块缩进，但 `get_text("dict")`
        中所有代码行的 x0 完全相同（106.60）——**PDF 文本层没有编码逐行缩进**；
      - 等宽字体可以可靠识别代码：C++ 书用 DejaVuSansMono，
        《CTF特训营》用 CourierNewPSMT；
      - 4 本扫描书没有文本层（OCR），没有字体/坐标信息。
  - 修复：
      - `build_pdf_segments`：按字体把 native 页拆成 code / paragraph 片段；
        判定用“行内出现等宽字体即 code”，不是“主导字体”——
        初版按主导字体时，代码块里的中文注释（中文字体）被拆成正文，
        代码块碎成一堆单行片段；
      - `reindent_c_like`：按花括号深度重建 4 空格缩进，
        忽略字符串与注释里的括号；
      - `to_elements` 每段一个元素，CODE 走 `normalize_code_text`，缩进不再被压平；
      - 新增 `tools/reingest_pdfs.src`：native 页重新解析，
        OCR 页直接复用已存文本，不重跑 OCR。
  - 结果：
      - PDF code 元素 **0 → 2008**；带缩进的 code 元素 **503**；
        代码行 26445，缩进行 **5340**；
      - 块级：**340** 个 PDF 块含 4 空格缩进行；
        C++ 书的 `szAsmData` 数组、`if` 体、结构体字段都已按层级缩进；
      - 扫描/OCR 书 code 元素仍为 0（无字体信息，原始缩进不可恢复）。
result:
  - **PDF 的“缩进”分两层**：文本层是否编码了位置/空白，和入库时是否保留。
    这 9 本书的文本层把所有代码行放在同一 x，只能重建块结构缩进，
    无法还原原书排版。
  - **字体是 native PDF 最可靠的代码信号。** 但判定要按行内字体并集：
    代码块里的中文注释常用中文字体，按“主导字体”会把注释拆成正文；
    C++ 书 215 行里 154 行含等宽字体。
  - **OCR 页面只能复用已有文本。** 不要把“缩进修复”宣传成对扫描件也生效；
    没有坐标/字体信息，后处理只能猜。
conclusion:
  - 修数据格式问题前先确认“原始数据里到底有没有这个信息”。
    文本层没编码的缩进，任何后处理都只能重建，不是恢复。
  - 重建也要有依据：花括号层级是可验证的结构，比“看起来像代码就加空格”可靠。
```
