```yaml
id: LAW-0034
prev: LAW-0033
date: 2026-11-12
source: 实验
topic: 超长代码块要先按“单行”切，再按行打包；巨型单 token 会让 token 统计失真
hypothesis: 4 个 >700 token 的块是行数太多、打包上限失效。
experiment:
  - 审计 15477 个活跃块，>700 token 的有 4 个，全部是 code：
      - 2172 token / 19543 字符 / **1 行**（`1.py` 的二进制串）；
      - 1200 token / 2177 字符（单行 2169 字符的 URL 编码 payload）；
      - 930 token ×2 / 2309 字符单行（hex payload）。
  - 根因：
      - `_pack_lines` / `_hard_split` 以“行”为最小单位，单行超过上限也整行塞进一块；
      - 旧的字符宽度回退只在“整块恰好只有 1 行”时触发，多行文件里的单行超长不处理；
      - `TOKEN_PATTERN` 把整段 base64/二进制串当成一个 token，token 统计对超长行失真，
        单靠 token 判断会认为它“只有 1 个 token”。
  - 修复：
      - 新增 `_split_line`：按 token 密度估算字符宽度，并设 8×chunk_size 的字符硬上限；
        仍超限的片段二分，直到 token 数落在 chunk_size 内；
      - `_pack_lines` 对每一行先 `_split_line`；`_hard_split` 统一走 `_pack_lines`；
      - 散文超长句也经过 `_split_line`，覆盖“一个巨型 token”的情况；
      - 代码块被切开后仍由 `_split_code` 给每片补围栏，不产生半截围栏。
  - 首次重切暴露新问题：`二进制高位补0/1.txt` 被切成 563 个片段，其中大量片段
    内容完全相同；`chunk_id` 由元素 + 内容哈希生成，不含位置，导致同一文档内
    ID 冲突（`UNIQUE constraint failed: chunks.chunk_id`）。
    修复：把块序号 `order` 纳入 `stable_id`；该文档 563 块全部唯一。
  - 结果：
      - 4 个异常块 2172 / 1200 / 930 / 930 token → 全库最大 **534** token
        （含 64 token 重叠窗口的余量）；>700 token 的块 **4 → 0**；
      - `1.py` 1 块 → 6 块；全库块尾未闭合围栏仍为 **0**。
result:
  - **“块太大”先看是不是“单行太大”。** 按行打包对单行无效；
    行内切分要同时看 token 密度和字符长度。
  - **token 统计不能当唯一尺度。** 两万字符的 base64 是一个 token；
    必须用字符上限兜底，否则切分器会认为它“很安全”。
  - **块 ID 必须包含位置。** 同一段内容被切成多个相同片段时，
    仅靠元素 + 内容哈希会碰撞；把 `order` 纳入 ID 才保证同文档内唯一。
  - 切代码行会破坏语法完整性，但这是检索粒度的必要代价；
    围栏补全和重叠窗口保证了可读性与上下文。
conclusion:
  - 切块器的最小单位应随内容变化：散文按句、代码按行、
    超长行再按字符预算切。
  - 任何“按单位打包”的循环都要问一句：单位本身超限时怎么办。
```
