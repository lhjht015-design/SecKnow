topic: 真实赛题的组合是"异构"的——状态必须能跨越 字符串 → 结构化参数
hypothesis: v009 的纯文本变换链可以推广到"先解码、再走结构化求解"的混合场景。
experiment:
  - 把规划器的状态值从 `str` 扩展为 `str | dict[str, int]`，新增类型 `int_fields`。
  - 新增两个单元：
      `parse_int_fields` : text → int_fields（认中英文标签、十进制/十六进制）
      `rsa_small_e`      : int_fields → flag（e>64 时主动拒绝，不硬算）
  - 题目：
      M1  base64("n=…,e=3,c=…")                → 解码 → 解析 → RSA（3 步）
      M2  hex("n=…")                            → 解码 → 解析 → RSA（3 步）
      M3  base64(hex(base64("n=…")))            → 三层解码 → 解析 → RSA（5 步）
      M4  中文标签 + 十六进制数值                → 解析 → RSA（2 步）
      N1  负样本：e=65537（不满足小公钥指数）    → **应失败**
      N2  负样本：4 字节重复密钥 XOR             → **应失败**
    每题再给"明说技术名"与"只描述行为"两种题面。
  - 结果：
      正样本 **8/8**（4 题 × 2 题面），负样本 **4/4 正确失败**。
      典型路径：`b64_decode → hex_decode → b64_decode → parse_int_fields → rsa_small_e`
      加 9 个诱饵单元后：beam 仍 8/8（224 节点），BFS 掉到 6/8（329 节点）。
result:
  - **异构组合可行**：流水线中段可以从字符串切换到结构化参数，再由结构化单元接管。
  - 关键设计点有三个，缺一不可：
    1. 状态值必须允许非字符串；
    2. 去重键要对结构化值做规范化（`json.dumps(sort_keys=True)`），否则同一份参数会被反复展开；
    3. 启发式要能处理非字符串状态（这里给结构化参数一个正向分，因为它本身就是进展）。
  - 两个负样本在两种搜索下都正确失败。特别是 N1：参数解析**成功**了，
    但 RSA 单元判断 `e=65537` 不满足小公钥指数条件，主动拒绝——
    这是"解析成功 ≠ 能解"的例子，也说明单元内部必须做适用性检查，不能硬算。
  - v009 的 beam 结论在混合场景下同样成立（14 个单元，beam 8/8 / BFS 6/8）。
conclusion:
  - 规划器不能假设"数据一直是文本"。真实题就是编码层 + 结构化层的混合，
    状态类型必须是开放集合，而不是只有 string。
  - **单元要对自己不适用的情况显式拒绝**（e 过大、c 不是完全幂、数据长度不符），
    否则会产出错误结果，把"解不出"变成"解错了"——后者危害大得多。
  - 至此，离线、零模型的解题链路已经有四段实测支撑：
    契约（LAW-0010）→ 形态路由（LAW-0011）→ 多步搜索（LAW-0012）→ 搜索控制（LAW-0013）
    → 异构状态（本 law）。
