topic: 围栏闭合要在解析层和切块层各修一次：缩进围栏、行内闭合、重复开围栏都会制造半截代码块
hypothesis: 不闭合围栏是切块时把代码块切断造成的（LAW-0031 的结论）。
experiment:
  - 审计 15395 个活跃块：
      - 按 `text.count("```") % 2` 统计：7 个“不闭合”；
      - 按前端真实判定（行首去掉空白后以 ``` 开头才算围栏）重算：
        **14 个块在块尾仍处于围栏内**——比子串统计更多，因为行内闭合围栏
        （`...}; ``` `）根本不会被任何行渲染器认成闭合。
  - 14 个全部来自 Markdown，根因有三层：
      1. 解析器 `FENCE = ^```...` 只认顶格围栏；列表里缩进 4 空格的
         ` ```c ` 被当成正文，代码块被拆成多个 paragraph 元素；
      2. 源文件把闭合围栏写在代码行末尾（`... }; ``` `），
         即使解析成代码元素，块里也只有开围栏没有闭围栏；
      3. `图片隐写.md` 里还有 `~~~python` 紧跟 ` ```python ` 的重复开围栏，
         解析器只认 ```，奇偶从这一处开始整篇翻转——后续代码块
         全被当成“闭围栏 + 正文 + 开围栏”的错位组合。
  - 修复：
      - `FENCE` 允许行首空白；Markdown 在解析前先对**整篇**做 `balance_fences`；
      - `balance_fences`：同时识别 ``` 与 ~~~，统一输出 ```；
        丢弃开围栏后紧跟的重复开围栏；行内闭合拆行；EOF 未闭合补闭围栏；
      - 切块器对 Markdown 块再做一次兜底平衡（`.py` 不补，
        避免把源码里的字面 ``` 改掉）；
      - 审计指标改为与渲染器一致的行首判定，不再数 ``` 子串。
  - 结果：
      - `文件上传漏洞.md` / `图片隐写.md` / `PHP反序列化漏洞总结.md`
        块尾未闭合 **0**（修复前各 1 个）；
      - 全库行首判定块尾未闭合 **14 → 0**；按 ``` 子串的奇数计数 7 → 4，
        剩余 4 个全是字面内容（代码里的三反引号、引用块里的 `> ```python`、
        行内提及 `$_=```.[].[]`），不是真围栏；
      - 前端：代码块完整，未闭合块不再把后续正文吞进 `<pre>`。
result:
  - **“块不闭合”不是切块独有问题。** 解析器不认缩进围栏，代码块在元素层
    就已经碎了；切块层只能补锅。两层都要修。
  - **一个重复开围栏会翻转整篇。** `~~~python` 后紧跟 ` ```python `，
    解析器忽略前者、把后者当开围栏，于是全部后续围栏奇偶颠倒；
    围栏规范化必须按“整篇”做，而不是逐块修补。
  - **判定口径要和渲染器一致。** 数 ``` 子串会把行内提及和元数据误报为围栏；
    行首（允许缩进）判定才是用户真正看到的行为。
  - **补围栏要限定格式。** 只对 Markdown 补；`.py`/文本里的 ``` 可能是
    字面内容，补了反而改坏源码。
conclusion:
  - 围栏问题按“解析 → 切块 → 渲染”三层排查：解析决定代码块是否完整，
    切块决定块边界是否带着成对围栏，渲染只负责认行首围栏。
  - 行内闭合是来源格式的缺陷，应在入库时规范化，而不是让每个渲染器各自兼容。
