topic: canary/PIE 绕过能做成单元，但"泄漏与利用必须同进程"以及"布局必须读反汇编"
hypothesis: 在 v014 的 pwn 单元基础上，加格式化字符串泄漏，就能绕过 canary 与 PIE。
experiment:
  - 新靶场 `vuln2.c` 两阶段：`printf(buf)` 泄漏 → `read()` 溢出。
    编三个变体：canary(no PIE)、PIE(no canary)、both。
  - 新增四个单元：
      `leak_stack`    发 `%p.`×60，解析泄漏值
      `find_canary`   低字节 0 且量级足够大的候选（栈地址排在后面）
      `find_pie_base` 用「低 12 位在 PIE 下不变」匹配 main/stage1/stage2 反推基址
      `frame_layout`  从反汇编推导缓冲区 / canary / 返回地址的偏移
  - 结果（连续跑 3 次均稳定）：
      C1 canary          → ✓
      P1 PIE             → ✓
      B1 canary + PIE    → ✓
      N1 无泄漏阶段       → ✓ 如实失败（`leak_stage_not_found`）
result:
  - **五个关键点**：
    1. **泄漏与利用必须在同一进程。** ASLR 每次运行都变，先跑一次拿泄漏、
       再跑一次用泄漏，必然失败。必须用交互式管道：发泄漏串 → 读到 `stage2:` →
       在同一进程里发 payload。这一条决定了实现方式，不是优化项。
    2. **栈帧布局必须从反汇编推导。** 我按"缓冲区 64 字节"算 canary 偏移，
       实际编译器给的是 `sub rsp,0x50`、canary 存在 `rbp-8`，
       于是 canary 偏移 72、返回地址偏移 88。差 8 字节 → canary 校验失败 →
       看似"泄漏对了但打不通"。
    3. **反汇编的字符串匹配有坑。** capstone 把 `fs:0x28` 渲染成 `fs:[0x28]`，
       写死 `"fs:0x28"` 会漏掉 canary 定位。匹配要容忍方括号。
    4. **候选必须靠执行验证，不能赌第一个。** canary 候选里会混入以 `00` 结尾的
       栈地址（如 `0x7f7800000000`）；基址候选也可能因低 12 位巧合而不唯一。
       正确做法：每次尝试重新起进程、重新泄漏，逐个候选验证，直到打出 flag。
    5. **没有泄漏原语时必须如实失败。** N1 没有格式化字符串阶段，
       系统返回 `leak_stage_not_found`，而不是硬猜一个 canary 继续打。
  - 耗时：单题 240–490 ms；负样本因为要等超时，约 6 s。
conclusion:
  - canary 与 PIE 的绕过不是"更难的算术"，而是**信息流**问题：
    先拿到运行时信息，再在同一进程里用掉。单元设计必须体现这条约束。
  - 布局推导、候选筛选这些环节**都必须可被真实执行证伪**。
    纸面上"缓冲区 64 字节"听起来天经地义，实际编译器给的是 80 字节的帧。
  - 泄漏类单元必须有明确的失败信号（`leak_stage_not_found` / `canary_not_leaked` /
    `pie_base_not_leaked`），不能把"没泄漏到"混进"解不出"。
next: ret2libc（需要 libc 版本识别 + 符号偏移）、格式化字符串任意写、
      以及把 v014/v015 的 pwn 单元接入通用规划器。
