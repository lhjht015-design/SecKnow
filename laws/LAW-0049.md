```yaml
source: 实验
topic: 工具适配层的价值在“多指令 gadget + 常驻执行进程”，不在替代题目映射
experiment:
  - 把 pwntools 放进常驻 WSL worker（stdin/stdout JSON 协议），
    封装 `ping / gadgets / build / run`；Windows 侧客户端按需启动、复用进程。
  - 复用 v030 的 P1/P2/P3/N1：
      self     自研（每次尝试起 wsl 进程）
      one-shot 每题起一个 wsl + pwntools
      adapter  常驻 worker
  - 结果（三组种子一致）：
      self 3/4，one-shot 4/4，adapter 4/4；
      总耗时 self 921 ms、one-shot 201 ms、adapter 131 ms；
      worker 初始化约 0.27–0.5 s（一次性，不计入单题）。
  - adapter 的 gadget 报告能识别 `pop rsi; pop rbp; ret`，自研扫描不能。
result:
  - **适配层真正买到的是两件事：gadget 覆盖 + 少起进程。**
    简单题（`pop X; ret`）两臂都行；差异出现在多指令 gadget 与执行开销上。
  - **常驻进程比“换工具”更关键。** 自研的主要耗时是每次尝试起一个 `wsl -e`；
    把执行放进 worker 后，单题从数百毫秒降到几十毫秒。
  - **适配层不改变“题目 → 工具”的映射。** 目标函数仍来自入口/字符串/调用图分析；
    适配层只负责“怎么打”和“打没打中”。
  - **执行边界要守住。** 适配层只在求解侧显式调用；产品 API 继续只读分析，
    不因为有了 worker 就去执行未知二进制。
conclusion:
  - 采用“自研负责理解题目，适配层负责成熟子问题”的分工；
    pwntools 当单元实现，契约与验证闸门保持不变。
```
