```yaml
id: LAW-0015
prev: LAW-0014
date: 2026-11-11
source: 实验
topic: 文件型载荷可行；但单元的能力边界必须收紧，否则会掩盖路由失效
hypothesis: 规划器状态加入 FileRef、按魔数识别类型后，真实附件题（zip/png/pcap/elf）可以自动串起来。
experiment:
  - 状态值新增 `FileRef`；按魔数识别 zip / png / pdf / elf / pcap / jpeg / gif / bin。
  - 新增文件类单元：unzip（支持嵌套）、read_text、png_text（tEXt/iTXt/zTXt）、
    pcap_strings、elf_strings、bin_strings；再复用 b64/hex/parse_int_fields/rsa。
  - 题目（每题给两种题面）：
      F1 文本附件                     → read_text
      F2 zip 内文本                   → unzip → read_text
      F3 zip 内 PNG 的 tEXt 藏 base64  → unzip → png_text → b64_decode
      F4 zip 套 zip                   → unzip → unzip → read_text
      F5 pcap 明文                    → pcap_strings
      F6 ELF 字符串表                 → elf_strings
      N1 随机二进制（负样本）
      N2 PNG 文本块是无关说明（负样本）
  - 首轮结果：12/12 正样本、4/4 负样本——**但 F5/F6 的路径是 `read_text` 一步搞定**。
result:
  - 追查发现：`read_text` 当时接受所有文件类型，它把整段二进制按 latin-1 解码，
    flag 恰好是明文就被"蒙对"了。**这只验证了 read_text，没有验证 pcap/elf 路由。**
  - 收紧 `read_text` 的 accepts 到 `{file:bin}` 后重跑：
      F5 → `pcap_strings`，F6 → `elf_strings`，F3 → `unzip → png_text → b64_decode`，
    依然是 **12/12 + 4/4**，但这次每条路径都走了预期的单元。
  - 平均展开 2.9 个节点、约 1.1 ms/题。BFS 与 beam 在这套类型化单元下结果相同
    （分支本来就少）。
conclusion:
  - **文件型载荷可行**：魔数识别 + 类型化单元 + 多步规划，可以把"给一个附件"变成一条可执行链路。
  - **单元必须只接受它真正擅长处理的东西。** 一个"什么都能读"的兜底单元会让测试假通过，
    也会在真实场景里用错误的方式处理数据（比如把 PNG 当文本读，得到一堆乱码还以为成功了）。
  - 这是 LAW-0009（自我泄漏）的同类问题：**测试通过不等于被测能力成立**，
    必须检查"它是怎么通过的"——看路径，不只看结果。
  - 兜底单元（bin_strings / read_text）应当排在最后，并且只在没有更具体的类型单元可用时启用。
next: 用真实比赛附件（不是自己构造的）复测；并把 unzip 扩展为"多成员选择"，
      因为真实压缩包往往有多个文件，需要决定解哪个。
```
