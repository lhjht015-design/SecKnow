topic: 解析/切片压缩空白会静默毁掉代码缩进；围栏必须在块边界保持闭合
hypothesis: 检索结果里的代码缩进与 Markdown 渲染问题，根因在入库阶段而不是显示层。
experiment:
  - 抽查 16361 个活跃块：
      - 含 ``` 的块 2978，其中 **51 个围栏不闭合**（切块把代码块从中间切开）；
      - **0 个块**有以两个空格/制表符开头的行；
      - elements 表里 4177 个 code 元素，**1818 个本身有缩进**，
        但块文本里只剩一列空格——`normalize_text` 的 `[ \t]+ → " "` 把缩进压平了。
  - 根因：
      - `domain/ids.normalize_text` 对所有文本压缩空白；
      - `text_parser.parse_markdown` 的 fence 缓冲与 `parse_plain` 的 .py 文本都走它；
      - `chunker._hard_split` 按行切分超长代码，切开后两半各自带半截围栏。
  - 修复：
      - 新增 `normalize_code_text`：保留行首空白与行结构，只规范行尾和空行；
      - Markdown fence 缓冲、.py 文本、CODE/TABLE 切片改用它；
      - 新增 `_split_code`：带围栏的代码块切片后，每片补上开/闭围栏。
  - 重新入库 `book/Des-CTF-Knowledge` 下 1347 个 markdown/text/py 文档
    （10080 块，107 s；未重跑 PDF OCR），随后重建 TF-IDF 与图（85.7 s）。
  - 修复后：
      - 含两个空格以上缩进的块 **1548**（修复前 0）；
      - 不闭合围栏 **5**（修复前 51；剩余是引用块里的围栏与字面反引号）；
      - 仍有 **1515** 个块以逗号/冒号/左括号等结尾——这是 token 上限导致的
        句中断块，属于另一类问题（UI 需要提示"下一块继续"）。
result:
  - **三个关键点**：
    1. **显示层修不了已丢失的数据。** 前端之前把缩进渲染成等宽也没用，
       因为块文本里根本没有缩进；必须先修解析/切片。
    2. **代码规范化必须与散文分开。** 散文压缩空白是对的；
       代码块需要保留行首空白、内部对齐与换行。一个 `normalize_text` 通吃，
       就会静默毁掉代码结构（又是"看起来正常、实际已经坏了"）。
    3. **切块要尊重结构边界。** 围栏是代码块的边界；按行数硬切会把围栏切开，
       下一块开头就是半截代码。切片后给每片补围栏，成本极低。
  - **仍未解决**：1515 个句中断块。修法是在 `_pack`/`_hard_split` 里
    优先在句末标点或空行处切，并在 UI 显示"内容可能在下一块继续"。
conclusion:
  - 知识库的"格式丑"有两层：数据层（缩进/围栏/图片）和显示层（Markdown 渲染）。
    这次先修数据层，再补显示层（围栏/表格/图片/引用块）；
    只有数据层正确，显示层才有意义。
  - 图片同理：482 个块引用图片，其中 45 个是语料内相对路径（全部存在），
    939 个是外链（离线不可用）。相对图片必须由 API 提供并以 `<img>` 渲染，
    外链只能显示"离线不可用"占位。
