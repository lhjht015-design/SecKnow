  - 新增两个单元：
      staged-call：先 gets(buf2) 写 /bin/sh，再 system(buf2)（ret2libc2）；
      ret2libc-leak：puts@got 泄漏 → 计算 system → 二次溢出（ret2libc3）。
  - 结果：解出 7/10（ret2text、ret2libc1、ret2syscall、ret2libc2、ret2libc3、
    leakmemory、overwrite）；contacts 拒绝；pwn3、ret2shellcode 不支持；连跑 3 次一致。
  - 过程里踩到的坑：
      - ret2libc3 泄漏偏移 112，但 main 重入后第二阶段偏移是 104；
      - stdio 会把多余输入缓冲在父进程，第二次 gets 之后的 shell 命令必须延迟发送；
      - 泄漏行里混着多个 GOT/PLT 值，必须按“libc base 页对齐”筛选；
      - 题目自带 libc 与本机运行时 libc 版本不同，偏移不能直接套用。
  - 工具层：pwntools 4.15 / ROPgadget 7.7 / capstone 6.0 / pyelftools 0.33 /
    LibcSearcher 1.1.5；LibcSearcher 多候选需二次校验。
result:
  - **多阶段利用不是“再加一个 payload”。** 进程要回到可再次输入的状态，
    偏移、输入时序、地址来源都会变；这些必须在同一进程内验证。
  - **偏移会漂移。** 同一函数重入后栈对齐可能不同，泄漏偏移不能直接复用。
  - **输入时序是协议的一部分。** stdio 预读会吞掉后续命令，必须分阶段发送。
  - **环境决定偏移。** 本地验证用 `elf.libc`；libc 数据库只能给候选，需页对齐/多符号校验。
conclusion:
  - 真题覆盖的提升来自“多阶段交互原语”，而不是更多 gadget；
    下一步是栈地址泄漏（shellcode）与 canary/堆布局（contacts）。
