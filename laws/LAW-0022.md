```yaml
id: LAW-0022
prev: LAW-0021
date: 2026-11-11
source: 实验
topic: 三保护组合（canary + PIE + ret2libc）可以做，但三样信息必须在同一进程里按顺序拿
hypothesis: 把 v015 的泄漏单元与 v016 的 ret2libc 单元串起来，就能打通三保护全开的靶场。
experiment:
  - 靶场 `vuln4.c`：`main{ while(1){ puts("input:"); vuln(); } }`，
    `vuln{ char buf[128]; read(0,buf,0x200); printf(buf); }`，
    编译 `-fstack-protector-all -pie -fPIE -O0`（canary + PIE + 系统 libc）。
  - 三段式，同一进程：
      round 1  `AAAAAAAA + "%p,"×N`：用标记值定位缓冲区在 varargs 中的下标 idx0，
               由此得到 canary（buffer + canary_offset）与保存的返回地址
               （canary 槽 + 2 个槽），再减 main 中的静态返回偏移得到 PIE 基址。
      round 2  `%<idx0+2>$s`，指针槽放 `PIE_base + puts@got`：泄漏 puts 运行时地址，
               减 libc 偏移得到 libc 基址并做页对齐校验。
      round 3  padding + canary + saved rbp + [对齐 ret] + pop_rdi + binsh + system。
  - 新增单元：`analyze_layout`（从反汇编推 buf/canary/ret 与 main 返回点）、
    `round1_leak`、`round2_leak`、`build_stage3`。
  - 结果（连续 3 次稳定）：
      T1  三保护全开                    → ✓ 约 1.18 s
      N1  用错 libc 偏移（模拟版本不匹配） → ✓ 如实拒绝（libc_mismatch）
      N2  没有可控的格式化字符串泄漏       → ✓ 如实拒绝（leak_failed）
result:
  - **六个关键点**：
    1. **三样信息必须同进程、按顺序拿。** canary 和 PIE 来自 round 1，
       libc 地址依赖 PIE 基址算出的 GOT 地址，ROP 又依赖 libc 基址。
       任何"跑一次拿泄漏、再跑一次用"都会因 ASLR 失败（LAW-0019）。
    2. **格式化字符串长度要按 canary_offset 严格限制。** `"%p,"` 是 **3 字节**
       （%、p、逗号），不是 2 字节。我按 2 字节估算，44 个值就写出 141 字节，
       超过 canary_offset=136，直接写坏 canary，报错是
       `*** stack smashing detected ***`——看起来像"利用逻辑错"，
       实际是**泄漏载荷自己踩了 canary**。公式应为
       `n = (canary_offset - 8 - 1) // 3`（8 字节标记 + 1 字节终止 NUL）。
    3. **read 不会补 NUL，printf 会继续读缓冲区残留。** 第 1 轮只写了 135 字节，
       136 之后的残留若含 `%`，printf 会把它当成新的格式说明符，轻则输出乱码、
       重则崩溃。发送的泄漏串末尾必须显式补一个 `\x00`。
    4. **idx0 必须用标记值现场标定。** 缓冲区在 varargs 中的起始下标随环境/栈布局变化；
       在 buffer[0] 放 `0x4141414141414141`，扫出它等于哪个 `%p`，
       之后 canary / saved rip 的槽位都按 `idx0 + 槽偏移` 计算，不写死下标。
    5. **`%s` 的指针要放在格式说明之后。** PIE 下 GOT 地址的高位含 `00`，
       若把指针放在 buffer 开头，格式串会立刻被截断。做法：
       先写 `LIBC:%<idx0+2>$s`，用空格补齐到 16 字节，再在偏移 16 放 8 字节指针。
    6. **栈对齐仍然需要一个额外的 `ret`。** rbp 在函数入口恒为 16 字节对齐，
       返回地址槽恒为 `rbp+8`；直接 `pop_rdi → system` 会让 system 入口
       rsp 错 8 字节。加一个 `ret` 后 system 入口 rsp ≡ 8 (mod 16)，实测成功。
  - 负样本的价值：N1 在 round 2 后基址不页对齐，返回 `libc_mismatch`；
    N2 根本没有 printf(buf)，round 1 的标记找不到，返回 `leak_failed`。
    两者都在 150 ms 内结束，没有硬猜 canary 或地址。
conclusion:
  - 三保护组合不是"三个独立技巧相加"，而是**一条信息依赖链**：
    fmt 泄漏 → canary/PIE → GOT → libc → ROP。单元设计必须显式表达这条链，
    每一环的失败都要有独立信号（leak_failed / pie_base_invalid / libc_mismatch / shell_failed）。
  - 泄漏载荷本身也要受 canary 约束——这是本实验最反直觉、也最容易静默出错的地方。
  - 至此 pwn 的四条主路径（ret2win、canary/PIE、ret2libc、三者组合）都已在真实进程上验证。
next: 堆利用（tcache/UAF）、格式化字符串任意写（%n）、stripped 三保护组合、
      把 pwn 单元接入通用规划器并按题面自动选择路径。
```
