source: 实验
topic: pwn 可以单元化，但有五个"不看就错"的实现细节
hypothesis: pwn 的标准套路（查保护 → 找 gadget → 测偏移 → 拼 payload → 执行）可以做成确定性单元，并在真实 ELF 上验证。
experiment:
  - 在 WSL(Ubuntu 22.04, gcc 11.4) 里编译三个真实靶场：
        vuln         无 canary / 无 PIE（正样本）
        vuln_canary  开 -fstack-protector-all（负样本）
        vuln_pie     开 -pie -fPIE（负样本）
    靶场用 gets() 造成栈溢出，并注册 SIGSEGV 处理器打印崩溃 RIP。
  - 四个单元：elf_info（保护+符号）、find_gadgets（capstone）、probe_offset（真实执行探测）、
    build_ret2win（拼 payload，含栈对齐）。
  - 结果：T1（ret2win）✓、T2（带参数的 ret2win，需要 pop rdi）✓、
    N1 canary 正确拒绝 ✓、N2 PIE 正确拒绝 ✓；平均 475 ms/题。
result:
  - **五个实现细节，每一个踩错都会得到"看起来对、实际错"的结果**：
    1. **裸字节扫描找 gadget 会落在指令中间。** 最初用 `data.find(b"\x5f\xc3")` 找
       `pop rdi; ret`，算出的地址 0x4011af 其实是另一条指令的尾字节；跳过去会执行
       完全不同的指令。必须用反汇编器（capstone）按**指令边界**找，
       并用符号地址当标准答案校验（本次 0x401517 与 `gadget_pop_rdi` 完全一致）。
    2. **内核会把非规范地址归一化成 nil。** 想用"崩溃地址反推偏移"时，
       崩溃行是 `addr=(nil) rip=0x4014fb`——因为覆盖的返回地址是字母（非规范）。
       可靠做法是：把已知标记（0xDEADBEEF）写进 payload，判断 **RIP 是否等于标记值**。
    3. **16 字节栈对齐。** 不加对齐时，跳进需要调用 libc 的后门会在 `movaps` 上崩；
       多加一个 `ret` gadget 把 rsp 调 8 字节后才成功。这是真实 pwn 最常见的坑之一。
    4. **canary 符号是未定义导入（st_value=0）。** 只收集"有地址的符号"会漏掉
       `__stack_chk_fail`，于是负样本没被拦住、白白跑了 512 次探测（73 秒）。
       检测保护要看**导入表**，不是可寻址符号表。
    5. **跨进程探测慢一个数量级。** 逐次从 Windows 起 `wsl -e` 每次几百毫秒，
       72 个偏移要 20 秒；把循环放进 WSL 内一个 python 进程后降到 0.5 秒。
  - 负样本必须**先拒绝、再动手**：canary 和 PIE 在进入探测之前就应当被拦下。
    先探测再失败，既浪费又容易误判成"偏移没找到"。
conclusion:
  - pwn 的标准套路确实可单元化，而且**每一步都能被真实执行验证**——
    这比 crypto/encoding 那批"纯数据变换"的单元更硬，因为它最终要打穿一个真的进程。
  - 但 pwn 单元的正确性依赖大量二进制细节，**必须用真实编译的靶场验证**，
    纸面推演会同时踩中上面五个坑。
  - 保护检查要作为**前置闸门**：canary / PIE 未处理时拒绝执行，
    并把原因如实返回（`canary_present` / `pie_enabled`），而不是"解不出"。
next: 补 canary 绕过（泄漏 -> 重打）与 PIE 基址泄漏两个单元，
      再把 pwn 单元接入通用规划器（目前是确定性流水线，不是 BFS）。
