```yaml
id: LAW-0025

date: 2026-11-11
source: 实验
topic: 文本召回与契约规划合并——召回只产候选，契约决定能不能用，跨家族拼接靠状态类型
hypothesis: 把 5 个文本数据单元与 8 个黑盒单元放进同一个 UNITS / recall / 规划器后，
            同一套机制能同时处理文本题与"给脚本"的题，并能跨家族组合。
experiment:
  - 统一单元库 14 个：
      基础设施（常驻，不参与召回竞争）：probe_facts / classify_structure /
        verify_plain / bytes_to_text
      黑盒策略：invert_bytewise_affine / invert_bytewise_table /
        invert_permutation / invert_gf2 / solve_prefix_checker
      文本数据：rsa_small_e / base64_chain / xor_single_byte / crc32_brute /
        caesar_brute
  - 规划器仍是 DFS + 回溯；只使用"召回结果 ∪ 常驻单元"，并按 accepts/guard 过滤。
  - 新增 P6：主办方脚本 = 先 Base64 再逐字节 S 盒。路径跨家族：
      probe_facts → classify → invert_bytewise_table → verify_plain
      → bytes_to_text → base64_chain
  - 结果（连续 2 次一致）：
      T1–T5 文本题            → 5/5
      P1–P6 黑盒题（含组合）   → 6/6
      N1–N4 负样本            → 4/4 如实拒绝
      正样本 11/11，负样本 4/4；总探测 16894。
result:
  - **四个关键点**：
    1. **召回与契约职责分离。** recall() 只按技法词产候选；规划器再用
       accepts / produces / guard 过滤。题面提到 RSA 不会让 oracle 单元被选中，
       反之亦然——两套世界在同一张表里但不互相污染。
    2. **基础设施单元必须常驻。** N1/N3 的题面没有任何技法词命中
       （recall=[]），但 probe_facts 仍在，所以仍能给出
       `not_length_preserving` / `nondeterministic` 的明确拒绝。
       如果拒绝也依赖召回，未知题会退化成"没有路径"而不是"知道为什么不行"。
    3. **跨家族组合靠状态类型，不靠特判。** P6 的
       `verified → bytes_to_text → text → base64_chain` 没有任何专用胶水代码；
       只要上一个单元产出 `verified`、下一个单元接受 `text` 就能接上。
    4. **同一份规划器处理两种输入。** 文本题从 `text` 状态出发，
       黑盒题从 `oracle` 状态出发；DFS、Refuse、验证闸门完全复用。
  - **诚实的限制**：
    - 文本召回仍是关键词匹配，LAW-0011 的结论不变：题目换名字后关键词召回
      会塌陷。本实验的文本题都保留了技法词，所以 5/5 **不代表**真实改名场景。
    - 黑盒题的成功依赖题面里出现"加密脚本/校验器/S盒/Feistel"等线索；
      若题面只给一个附件、不提技术名，召回会漏，需要按文件类型/魔数另开入口。
conclusion:
  - 合并的价值不是"更强的召回"，而是**一个库、两套输入、同一套决策与验证**。
    黑盒策略从此不是独立实验，而是和 RSA/Base64 单元平级的条目。
  - 召回失败时系统仍能诚实拒绝（常驻单元），召回成功时能跨家族拼接
    （状态类型连接）。这两点共同保证"不知道就说不知道，知道就拼得出来"。
next: 按附件魔数/后缀自动建立 oracle 入口（不依赖题面出现"脚本"二字）；
      文本召回加入 L2/L3 形态特征，缓解 LAW-0011 的改名塌陷；
      把 angr 符号执行作为新的 strategy 单元接入同一规划器。
```
